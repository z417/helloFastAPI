# 统一开发工作流协议 (Universal Developer Workflow Protocol)

> [!IMPORTANT]
> 本规范为通用软件工程设计，禁止耦合任何特定项目的私有业务或局部框架。

---

## 一、任务分流机制：基于复杂度的双链路决策

AI 接收任务后，必须自动根据下表进行**任务复杂度判定**，自驱动分流至不同的执行链路：

| 判定维度 | 复杂任务 (A 链路 - 轻量设计锁控制) | 简单任务 (B 链路 - 波次自愈机制) |
| :--- | :--- | :--- |
| **数据库** | 涉及数据表 Schema 变动、唯一性索引修改或数据迁移 | 仅普通的数据读写、非核心字段赋值 |
| **并发与安全** | 涉及并发安全控制、底层引擎重构或连接池状态修改 | 常规的异常捕获补充、日志信息输出 |
| **受阻范围** | 涉及跨模块核心 API 重新定义、鉴权流与全局中间件修改 | 局部逻辑优化、拼写纠正、前端表现层状态恢复 |

### A 链路：复杂任务（口头设计确认协议 - Design Consent Lock）
为了防止繁琐的物理文档管理拖慢节奏，系统采用极其高效的**口头设计确认锁**：
1. **设计规格输出**：AI 绝对禁止直接输出具体业务代码，必须首先在对话中输出一段 **5-10 行的极简 YAML 架构预览**。
2. **人类授权确认**：AI 必须静默等待。当人类回复类似 "Yes" / "Approved" / "好" 后，设计锁解除，方可开始编码。

```yaml
task_spec:
  name: "任务物理名称"
  scope_files:
    - "变更影响的物理文件路径"
  strategy: "修改方案、选型权衡及边界处理"
  verification_commands:
    - "回归与单元测试执行指令"
```

### B 链路：简单任务（自愈与吞吐模式）
1. **合并吞吐**：允许在单次回复中连续执行原子任务（单次最多 3 个原子修改）。
2. **回归检验**：每个原子步骤执行后必须立即触发回归测试验证。

## 二、开发核心工作流 (Core Development Workflow)

1. **渐进式开发 (Iterative Development)**：
   - 采用多轮对话迭代的方式逐步明确并实现需求。
   - **调研先行**：在着手任何设计或编码工作之前，必须完成前期调研并厘清所有疑点，严禁盲目设计与编码。
2. **结构化流程 (Structured Workflow)**：
   - 严格遵循 **“构思方案 → 提请审核 → 分解为具体任务”** 的作业顺序进行。
   - 该原则在复杂任务（A 链路）中通过 YAML 架构预览与口头设计锁进行实体化约束。

---

## 三、三击熔断与自愈机制 (3-Strike Fail-Safe)

在调试局部 Bug 或执行简单任务时，若**连续失败达到 3 次**，必须立即启动 Fail-Safe 自愈保护：
1. **停止执行**：立即终止当前修改循环，防止继续生成无意义代码或引入二次污染。
2. **状态现场转储 (State Dump)**：将当前的断点现场、失败报错日志、已修改文件以及临时排查分析等关键上下文，强制写入当前项目的状态追踪文档（`.gsd/STATE.md`）。
3. **开辟干净会话**：在输出中向人类给出转储成功的反馈，并明确建议人类开启干净的新会话，彻底打破上下文死循环幻觉。

---

## 四、任务执行与客观验证自检

1. **客观实证原则 (Empirical Proof)**：
   - AI 代码修改完成后，**严禁口头宣称“代码已修复”**。必须在对话末尾呈递真实的测试运行输出作为客观实证。
2. **纯表现层变更豁免**：
   - 若改动仅涉及markdown文件、非业务静态资源或前端纯样式展现层，可豁免执行底层逻辑或 API 的单元回归测试。
